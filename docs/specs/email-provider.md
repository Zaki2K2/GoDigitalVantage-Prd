# Email provider specification

Status: reviewed implementation contract, before code changes (2026-10-19).

- Central backend-only Resend adapter; no SDK or public arbitrary-send endpoint. Existing cookie authentication, CSRF, reward ownership, token hashing, claim CAS, expiration and audit remain authoritative.
- Sending domain is mail.godigitalvantage.com. Sender addresses use configurable RESEND_FROM_EMAIL (notifications), RESEND_REWARDS_FROM_EMAIL (rewards), RESEND_VERIFY_FROM_EMAIL (verification/OTP), RESEND_SECURITY_FROM_EMAIL (reset/security). Display-name syntax is validated; every sending address must use this exact domain. Do not fall back to old sender variables or another domain.
- EMAIL_PROVIDER=resend; EMAIL_ENABLED=false by default, parsed strictly (the string false must never become true). Empty optional secrets are treated as absent. Sending requires enabled flag, API key, webhook signing secret, correct sender and HTTPS app origin in production. Reward cryptographic secret remains separate.
- Before any production-mode send, read Resend domains (bounded paginated lookup) and require this exact domain to have status verified and sending capability enabled. Failed/unavailable/domain-read-denied status fails closed. No domain creation, DNS mutation, secret modification, enabling or deployment is performed by this task.
- Reusable escaped HTML + text templates: reward, verification link, OTP, password reset link, claim confirmation and notification. Templates only render data; they do not create OTPs/reset tokens, implement new auth flows or mark accounts verified. Existing reward issuance/verification uses these templates. Claim confirmation is available to callers; it must not make email success a prerequisite of a committed claim.
- OTP/reset/verification links must use the application's origin; HTTPS in production. Never persist rendered bodies, OTPs or raw tokens in email telemetry. Do not add support reply-to without confirmed receiving mailbox configuration.
- Resend receives deterministic body, purpose-specific sender, Idempotency-Key and an eight-second combined network budget (domain lookup plus submission), within the existing Vercel function budget. Retry using the same payload/key within 20 hours; never automatically retry with a new key. Different-payload key conflicts are explicit EMAIL_IDEMPOTENCY_CONFLICT; network/429/5xx are EMAIL_SEND_UNCERTAIN; definitive provider rejection is EMAIL_SEND_FAILED. No background timers or fire-and-forget sends on Vercel.
- Both POST /api/v1/webhooks/resend and the existing /api/v1/webhooks/instant-rewards/email accept raw JSON, bounded 100KB, signed Svix headers, constant-time HMAC check, five-minute timestamp tolerance. Validate before storage. Delivery/failure/bounce/complaint/suppression events persist in email_delivery_events with unique event ID, provider message ID, event type and timestamps only. Duplicate callbacks are safe. Reward receipts retain existing lifecycle/audit behavior; late receipts cannot roll back terminal states. Reconcile receipts received before provider acceptance was persisted.
- Provider acceptance is not delivery. Delivery requires a signed delivered event; failures, bounces and complaints remain distinguishable in generic telemetry. Unknown events are acknowledged without modifying rewards.
- No changes to production secrets, local secrets, DNS, provider resources, UI or deployed settings. Examples leave secrets blank and EMAIL_ENABLED=false.

Acceptance/tests: strict configuration parsing and disabled gate; all sender categories and escaping; wrong-domain/missing-secret/unverified/inactive-domain rejection; domain pagination/failure; stable idempotency body and 20h bound; sanitized transport failures; signed/invalid/replayed webhook receipts; reward lifecycle regression and receipt reconciliation. Run API suite, frontend regression, typecheck, lint and production builds. Document manual DNS, sender, signing-secret and Vercel configuration, with no claim of live delivery.

Primary provider contracts: [domains](https://resend.com/docs/api-reference/domains/list-domains), [signature verification](https://resend.com/docs/webhooks/verify-webhooks-requests), [idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys).

## Restricted free-tier test mode (reviewed before implementation)

- EMAIL_TEST_MODE is strictly parsed true/false, default false. EMAIL_ENABLED remains the independent master switch, default false. No changes to deployed variables or secrets.
- RESEND_TEST_EMAIL is an optional normalized single email address. When test mode is enabled, missing/invalid configuration fails closed. Only an exact normalized recipient match is allowed; never redirect or replace another recipient with the test inbox. Reject before any provider/domain API request with EMAIL_TEST_RECIPIENT_BLOCKED. The configured address must be the Resend account email; provider restrictions still apply.
- RESEND_TEST_FROM_EMAIL defaults to GoDigitalVantage <onboarding@resend.dev>, supports existing display-name validation, and must resolve to exactly onboarding@resend.dev in test mode. All template purposes use it only in test mode. Production sender validation continues to reject resend.dev and require mail.godigitalvantage.com.
- Restricted mode bypasses only custom-domain lookup/verification; it preserves EMAIL_ENABLED, API key, webhook signing secret, HTTPS production origin, idempotency/timeout checks, recipient validation and all reward ownership/token/claim requirements.
- Blocked email attempts have no provider message ID and cannot mark rewards SENT/DELIVERED or establish verification/claim proof. Existing failure audit/status behavior remains; fake delivery and automatic claim are forbidden. Successful test submission is acceptance only; signed webhook remains the sole delivery evidence.
- Examples leave EMAIL_ENABLED=false and EMAIL_TEST_MODE=false, RESEND_TEST_EMAIL blank; provide opt-in API Vercel settings using the actual frontend origin. Tests cover allowed normalized account recipient, blocked recipients with no fetch, missing/invalid configuration, disabled master switch, sender isolation, and reward claim/delivery safety on blocked send. Preserve production verification tests and reward regressions.
