# Decisions (✅ made · ⏳ assumed, pending stakeholder approval)
- ✅ Modular monolith; Express + Mongoose + Zod; Angular 20 standalone/SCSS (CLI v20 because Node 22.19 is below CLI 21's minimum).
- ✅ Auth: httpOnly cookie access+refresh, CSRF header check (user choice).
- ✅ Dev Mongo: local `mongodb://localhost:27017`; tests use `gdv_test`. No Docker/memory-server.
- ✅ API is CommonJS under TS `module: Node16`; tests via Vitest + supertest.
- ⏳ D01 phone/email optional · D02 multi-business in DB, one in UI · D03 edits publish new version · D04 review link on page (everyone) + SMS (eligible) · D05 review-SMS consent NOT finalized: send only with explicit opt-in until legal advice · D06 missed-call is P1 · D07 mock adapters, provider TBD · D08–D10 billing last · D11 never show Google review counts · D12 retention TBD · D13 no staff logins · D14 five question types · D15 no silent identity merge.
- ✅ M-AUTH: password hashing = Node `crypto.scrypt` (no extra dep); refresh tokens opaque, stored as HMAC, rotated per use, family revoked on reuse; access JWT 15m (disabled users lose access within 15m, refresh blocked immediately); CSRF = double-submit cookie on all unsafe methods (future inbound webhooks must be mounted outside `csrfProtection`); login limiter per IP+email (failures only), in-memory store → move to Redis if API scales horizontally; set `trust proxy` when deployed behind a proxy.
- ✅ Register with existing email returns 409 EMAIL_TAKEN (enumeration accepted until email verification exists).
- ✅ Dev API port is 3100 (3000 is occupied by another local project, `virtualfit-ai`).
- ✅ M-BIZ: slug generated server-side from the name (suffix on collision), immutable via API; users may hold several businesses in the DB but the UI uses the first (D02). Duplicate-submit protection = client `createRequestId` unique per owner (UI renews it when the form data changes). Non-members get 403 (not 404). Owner-only writes; `member` is read-only. Category is free text with suggestions (SRS gives no list). Logo upload deferred: `logoRef` exists but has no UI. Onboarding is never completed in M1.
- ✅ Refresh race: a token rotated <10s ago in a still-alive family is accepted again (multi-tab race); outside the window, reuse revokes the family (`familyRevoked`).
- ✅ Reproducible install: `apps/api/package-lock.json` regenerated on Windows so it carries the platform rolldown bindings; verified with `rm -rf node_modules && npm ci`.
- ✅ M-FORM/M-QR: draft = single document with optimistic `draftRevision`; whole-draft PUT covers add/edit/delete/reorder; versions insert-only; default 3-question draft created with the business (lazily for older ones). Preview = client render of the unsaved draft (no endpoint). QR generated server-side (`qrcode` dependency); URL = `PUBLIC_BASE_URL/r/<immutable slug>`; no scan events yet (`qr_events` deferred to M3). Public form is view-only and says so; no submit control exists.
- ✅ Refresh grace window (10s) analysis: a just-rotated token can be replayed inside the window by anyone holding it (e.g. a stolen cookie), which also hides the theft from reuse detection during that window. Mitigation applied: grace-path requests receive a new access token only (15 min), never a new refresh token, and only while the family is not revoked; after 10s any replay revokes the whole family. Residual risk: up to 15 min of access for an attacker who replays within 10s; accepted. Shrink `REUSE_GRACE_MS` if multi-tab races prove rare in practice.
- ✅ Install rule: after adding/removing API dependencies run `rm -rf node_modules package-lock.json && npm install` (an in-place `npm i` drops rolldown's platform entries from the lock, npm bug #4828) and verify with `npm ci`.
- ✅ Public pages (`/r/*`) skip the session probe; anonymous visitors cause no auth requests.
- ✅ M3 submission: client sends an `idempotencyKey` (one per page load); unique (businessId,key) makes retries/concurrent submits return the original response (200, `duplicate:true`). Contact upsert and consent grants are idempotent too (consent unique on (businessId,submissionKey,purpose)); a replay re-applies consent from the stored snapshot to heal a crash between steps.
- ✅ Version rule: a submission is validated against the version in the body if it is a published version of that business (customer may have loaded v1 while owner published v2; versions are immutable so this is safe), else the current one. Unpublished/unknown versions -> 404.
- ✅ Contacts: created only with an email or phone (name alone -> 422). Match phone first, then email, always inside one business. Public submitters only fill empty fields; they never overwrite an existing name/email/phone (prevents record poisoning by typing someone else's number). Phones need a country code (no default country exists).
- ✅ Consent: two optional purposes, `review_request_sms` and `marketing_sms`; checkboxes start unticked and are disabled without a phone; only explicit grants are stored (an unticked box is "no grant", not a withdrawal). Withdrawal/STOP handling and suppression are M4. Submitting feedback never implies consent. Wording text + version is snapshotted on every grant. Contact `consent.*` dates are a cache of the latest grant.
- ✅ Rating = first answered rating question (1-5); dashboard average is over responses that have one. Google review counts/ratings are not tracked or invented; the UI says so.
- ✅ Scan tracking: the public page POSTs `/public/:slug/scan` once per load (the data GET and asset requests are not counted). One scan per visitor per business per 30 min; visitor key = HMAC(ip|UA|businessId) salted with the UTC date, so it cannot be reversed or linked across days; no raw IP/UA stored; common crawlers ignored; rows expire after 400 days. Counts are "unique visitor windows", not people; shared NAT + same UA undercounts. `trust proxy` is still unset, so behind a proxy all visitors would share one IP (deploy blocker, same as rate limits).
- ✅ Spam: honeypot field (fake 201), per-IP in-memory rate limits, length caps, strict body schema, 100kb body limit. No CAPTCHA (would need a third-party service). Limiters are per process.
- ✅ Search over responses uses escaped regex on answer text/choice labels and matching contacts (no text index): fine at pilot volumes; add a text index or search collection if lists grow.
- ✅ Dashboard day buckets use the business timezone (`$dateToString` with timezone); the trend window is the last N calendar days.

## Current decisions, 2026-10-16 redesign

- Earlier M1/M2 entries are historical: public submission and scan events were delivered in M3. Existing membership authorization, immutable questionnaire versions/response snapshots, CSRF, and consent behavior remain authoritative.
- D02 updated: the UI supports selecting among the signed-in user's existing business memberships. The selection is saved per user in localStorage, applied to API-returned authorized businesses, and resets the view on switching. Tenant access still depends exclusively on server membership checks. Creating/inviting staff and managing locations remain future work.
- Bootstrap 5.3.8 is included as a selected Sass subset alongside existing utility layouts. Bootstrap Icons 1.13.1 uses a local SVG sprite; Outfit Variable 5.3.0 is bundled locally. No Angular component wrapper is needed for the current native controls. Existing TailAdmin-derived styling was retained, not newly imported. Asset licenses are distributed in `public/assets/`.
- Appearance has light/dark/system choices, persisted on the browser. Settings reads the real signed-in account; unavailable modules are labeled planned instead of presenting controls with no backend behavior.
- `PUBLIC_APP_BASE_URL` is the preferred QR origin/path, accepting HTTP(S) without credentials, query strings, or fragments. It takes precedence over the supported legacy `PUBLIC_BASE_URL`; generated URLs retain `/r/<immutable slug>` for compatibility. Reprinting is needed if the reachable network origin changes, even though the slug remains stable.
- Offline means a connected local LAN with Angular, Express, and MongoDB running. The browser uses relative `/api` through the Angular :4200 proxy to API :3100. There is no disconnected-client queue/PWA submission. Google review links and future external messaging still need internet.
- UUID-formatted client IDs use `crypto.getRandomValues` rather than secure-context-only `randomUUID`, preserving idempotency on phone HTTP LAN origins. QR PNG/SVG assets are generated entirely by local `qrcode`, with a four-module quiet zone.
- Smile Score is `100 × (4-star + 5-star responses) / rated responses`, rounded for display, with sample size and no value when there are no ratings. It is all-time, questionnaire-derived, and not a Google review score or benchmark. Scan counts are deduplicated visitor windows; no unsupported scan conversion metric is displayed.
- Product sequencing is documented in `docs/product-plan.md`: reliable feedback collection, meaningful existing analytics, and clear UI first; account recovery/export/staff workflow before AI, benchmarks, campaigns, or billing. No reference website/video analysis was available to inspect.
- ✅ Rewards: rule = template; presets served by the API. A low rating (default <=2) matching an enabled rule creates an incident and, if eligible, a reward (auto or owner-approved). Lowest matching `maxRating` rule wins. Rewards never depend on Google reviews or positive ratings; there is no review field anywhere in the module and the customer card says so.
- ✅ Anti-abuse: one reward per response (unique index); rolling cooldown per identity + atomic window reservation; total/daily caps via conditional upsert counters. Identity = HMAC of phone (else email) or, for anonymous customers, ip+user-agent (stored only as a hash). Residual risk: a determined person can change device/UA/phone to get another reward; mitigated by caps, approval mode, cooldown and staff verification.
- ✅ Codes: 8 Crockford-base32 chars (40 bits) from the CSPRNG, unique per business, stored in plain text (staff must read and share them), verify/redeem limited to authenticated members at 60/min. Customer links are stateless signed tokens (`<rewardId>.<hmac>`), nothing to enumerate.
- ✅ Redemption is atomic and idempotent by `requestId`; minimum spend needs an order total; discount = percent (capped by maxDiscount) or fixed (never above the order). Expiry is derived at read time (no cron).
- ✅ Roles: only owner/member exist. Owner = rules + decisions + manual issue; member = verify/redeem/share. No separate "admin".
- ✅ Delivery: no WhatsApp/email provider is configured anywhere in the project (SMS arrives in M4 with mock adapters). The module offers copy-link and `wa.me`/`mailto:` links that staff open themselves and records them as "shared by hand"; it never claims a message was sent or delivered.
- ✅ Money honesty: the dashboard reports discount cost only from totals staff entered at redemption (by currency) and counts redemptions without a total. It does not estimate or show recovered revenue (needs verified purchase data).
- ✅ UI: built in the app's existing design system (Tailwind template + Bootstrap foundations/icons already in the project) instead of adding a second Bootstrap layer. Local-first: no external services are used by issuing, showing or redeeming coupons.
- ✅ Vercel test deploy: `apps/web` is a standalone Vercel project (`vercel.json`: build `npm run build`, output `dist/web/browser`). `/api/*` is rewritten to the separately hosted Express API so the browser stays same-origin (httpOnly cookies + CSRF keep working, no CORS/cross-site cookies); the rewrite destination placeholder must be replaced. The API stays off Vercel Functions (long-lived Mongo connection, in-memory rate limiters, cookies). `TRUST_PROXY` (hop count) makes `req.ip` the real client behind the proxy chain.
- ✅ Vercel Hobby, two projects: `apps/api` runs as one Vercel Function (`api/index.js` -> `dist/vercel.js`, built by `tsc`; all paths rewritten to it) and `apps/web` rewrites `/api/*` to the API project so the browser stays same-origin. Mongo connection is cached per warm instance (`src/db.ts`). Rate-limit counters move to MongoDB with `RATE_LIMIT_STORE=mongo` (`rate_limits`, atomic pipeline upsert + TTL); local dev and tests keep the in-memory default. Reward cooldowns/caps and scan dedupe were already Mongo-backed; no other process memory or filesystem state exists.

- Admin uses explicit USER/SUPER_ADMIN DB privileges and safe inclusion projections; normal business endpoint permissions are unchanged. Standalone MongoDB remains supported; audit intent precedes mutation with crash-visible pending outcome. Business role/ownership changes now serialize per business and require another active owner before owner demotion/removal. Read-only inspection replaces impersonation. See [admin](admin.md).

## Instant Rewards decisions (2026-10-19)

- A delegated global `instant_rewards:manage` permission grants only this module. Business ownership alone grants none. Super Admin controls delegation with existing serialized/audited administration and session invalidation.
- There is no trusted global verified-email flag: separate one-time email challenge proves ownership per reward; the no-extra-verification policy still requires the original emailed claim token. User ID and current normalized email must both match bound rewards.
- A single MongoDB conditional document update records entitlement plus durable audit event. This supports standalone local MongoDB without introducing replica-set-only transactions. Claims reveal a code and receipt; no wallet/payment/real-world fulfillment is fabricated.
- Persist only token hashes and non-bearer random operation nonces. A dedicated server HMAC secret reconstructs identical provider-idempotent retries; no raw email bodies/tokens are stored. Rotate links with explicit resend; retry pending sends with their existing UUID within 20 hours.
- Use Resend HTTPS adapter and signed raw Svix webhooks. Acceptance is SENT; DELIVERED requires authenticated provider evidence. Missing sender/configuration produces visible stable errors. Existing business recovery reward delivery remains unchanged.
- Email links use fragments, immediately scrubbed, with inline existing login and in-memory token retention. No token returnUrl/storage/GET endpoints.
- Expiry is checked on every mutation and derived on every DTO; bounded lazy synchronization appends expiry events. Retain all timestamps and audit history.

## Shared email provider (2026-10-19)

Use mail.godigitalvantage.com only; configurable display-name sender aliases and EMAIL_ENABLED=false. Require live provider verification and sending capability before submission; use no new dependency. Preserve existing secrets; no provider/DNS/deployment writes. Support reply-to omitted until receiving mailbox confirmation. OTP/reset/claim-confirmation are reusable templates, not newly activated auth or automatic post-claim flows.

## Restricted email testing

Restricted Resend test mode is opt-in and independent of EMAIL_ENABLED. Only exact normalized RESEND_TEST_EMAIL is allowed; no redirection. RESEND_TEST_FROM_EMAIL must resolve to onboarding@resend.dev; production senders remain restricted to mail.godigitalvantage.com. Test mode bypasses custom-domain lookup only, retaining webhook/HTTPS/token/auth/idempotency controls.

## Campaign Management Engine

M-CAMP (2026-10-20): tenant-bound platform campaigns; configuration-only templates; existing discount reward issuance/redemption and Resend provider; owner/member permission mapping; bounded bearer-triggered serverless worker; no TTL takeover for unknown external-send locks. Email only; no invented channels/events. See [campaigns](campaigns.md) for semantics, migration, operational reconciliation and limits.
